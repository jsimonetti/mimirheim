# Plan 68 — config-editor: registry, field vocabulary migration, transactional save

## Purpose

Replace `_load_helper_models()`'s hardcoded `try`/`except ImportError` chain
with file-based schema discovery, build the per-entry-with-context
composition and transactional save described in
`mimirheim_helpers/config_editor/SPEC.md`, and migrate every Pydantic
config model's field annotations to the vocabulary SPEC.md §4 specifies.

This plan is backend-only. `static/app.js`, `static/style.css`, and
`static/index.html` are not touched — the current frontend keeps working
throughout, via deprecated endpoint aliases, until plan 69 deletes both the
old frontend code and the aliases.

Read `mimirheim_helpers/config_editor/SPEC.md` in full before starting,
especially §2 (Discovery), §3 (`x-mimirheim` envelope), §4 (Field
vocabulary), §5 (Document composition), §7 (Validation model), §8 (Save
semantics), §9 (Enabled state), §10 (Rejection rules), and §13 (Limits).
This plan implements that specification; it does not re-derive it. Where
this plan and SPEC.md disagree, stop and raise it — do not silently follow
either one.

## Decisions

### 1. New module: `registry.py`

`mimirheim_helpers/config_editor/config_editor/registry.py`. Pure discovery,
meta-schema validation, rejection handling, context composition, and
document validation logic. No HTTP imports — unit-testable standalone,
independent of `ConfigEditorServer`.

### 2. Bundled schema location and generation

`config_editor/schemas/bundled/*.schema.json`, one file per entry
(`mimirheim.yaml` itself plus every helper), each carrying its
`x-mimirheim` envelope (SPEC §3). Generated by extending
`scripts/generate_schema_json.py` to also emit these, committed, and
covered by the same drift test pattern already used for
`mimirheim/config/schema.json`.

`x-mimirheim.python_package` values, one per entry:

| Entry | `file` | `category` | `python_package` | `python_model` | `exclusive_group` | `required` |
|---|---|---|---|---|---|---|
| mimirheim | `mimirheim.yaml` | `core` | `mimirheim` | `mimirheim.config.schema:MimirheimConfig` | — | `true` |
| nordpool | `nordpool.yaml` | `prices` | `nordpool` | `nordpool.config:NordpoolConfig` | — | `false` |
| zonneplan | `zonneplan.yaml` | `prices` | `zonneplan_prices` | `zonneplan_prices.config:ZonneplanPricesConfig` | — | `false` |
| pv-fetcher | `pv-fetcher.yaml` | `pv` | `pv_fetcher` | `pv_fetcher.config:PvFetcherConfig` | — | `false` |
| pv-ml-learner | `pv-ml-learner.yaml` | `pv` | `pv_ml_learner` | `pv_ml_learner.config:PvLearnerConfig` | — | `false` |
| baseload-static | `baseload-static.yaml` | `baseload` | `baseload_static` | `baseload_static.config:BaseloadConfig` | `baseload` | `false` |

### 3. Meta-schema

`config_editor/schemas/_meta/mimirheim-helper-schema.meta.json`, written in
this plan against SPEC §10's rejection table. Every one of the 13 rules gets
an adversarial fixture and a test asserting the specific rejection.

### 4. Dependency

Add `jsonschema` to the `config-editor` extra in `pyproject.toml`.

### 5. Context composition is rebuilt per request, not cached

`GET /api/entry/<id>` always rebuilds `context` (SPEC §5) from whatever
`mimirheim.yaml` currently contains on disk at request time. No in-memory
cache of `context` is kept across requests — a stale cache would need
explicit invalidation on every `mimirheim.yaml` save, which is more moving
parts than re-reading one small YAML file per request costs.

### 6. Exclusive-group deletion, generically

Save logic reads `x-mimirheim.exclusive_group` from the registry rather than
a hardcoded list. `_baseload_variants` is deleted; the three baseload
schemas' shared `exclusive_group: "baseload"` (Decision 2 table) reproduces
the same behaviour generically.

### 7. `python_model` second pass

For a bundled entry with `x-mimirheim.python_model` set: after the
`jsonschema` pass succeeds, import the dotted path
(`importlib.import_module` + `getattr`), construct the model from the
submitted dict, and catch `pydantic.ValidationError`. Map each
`ValidationError` item's `loc`/`msg` into the same per-entry error list
shape the `jsonschema` pass produces (SPEC §12), so the frontend never has
to distinguish which validator raised.

### 8. MQTT redaction, IP allowlist, body size cap, path safety carry over unchanged

`MQTT_ENV_REDACTED`, `_REDACTED_MQTT_FIELDS`, `MAX_REQUEST_BODY_BYTES`,
`_safe_join`, and the `CONFIG_EDITOR_ALLOWED_IP` check are not being
replaced — they are wired onto the new endpoints exactly as they work on the
existing ones today.

### 9. Deprecated aliases stay until plan 69

`GET /api/schema`, `GET /api/config`, `POST /api/config`,
`GET /api/helper-configs`, `GET /api/helper-schemas`,
`POST /api/helper-config/<filename>` remain, reimplemented as thin adapters
over `registry.py`, so `app.js` keeps working unmodified through this plan.
Plan 69 deletes them once the new frontend no longer calls them.

### 10. Field vocabulary migration

SPEC §4 removes `ui_label`, `ui_group`, `ui_placeholder`,
`ui_instance_name_description`, and `ui_source` entirely. This plan performs
that migration across every file that carries them:

`mimirheim/config/schema.py`,
`mimirheim_helpers/pv/forecast.solar/pv_fetcher/config.py`,
`mimirheim_helpers/pv/pv_ml_learner/pv_ml_learner/config.py`,
`mimirheim_helpers/prices/zonneplan/zonneplan_prices/config.py`,
`mimirheim_helpers/prices/nordpool/nordpool/config.py`,
`mimirheim_helpers/reporter/reporter/config.py`,
`mimirheim_helpers/baseload/homeassistant/baseload_ha/config.py`,
`mimirheim_helpers/baseload/homeassistant_db/baseload_ha_db/config.py`,
`mimirheim_helpers/baseload/static/baseload_static/config.py`,
`mimirheim_helpers/scheduler/scheduler/config.py`,
`mimirheim_helpers/common/helper_common/config.py`,
`mimirheim_helpers/config_editor/config_editor/config.py`.

Rewrites, per field:

- `ui_label` → `Field(title=...)` (the standard keyword; drop
  `json_schema_extra` entirely if `ui_label` was its only key).
- `ui_group: "advanced"` → `json_schema_extra={"x-category": "Advanced"}`.
  `ui_group: "basic"` → drop; no replacement (SPEC §4).
- `ui_source: "pv_arrays"` → `json_schema_extra={"x-enumSource": "#/context/pv_arrays"}`.
  `ui_source: "static_loads"` → `json_schema_extra={"x-enumSource": "#/context/static_loads"}`.
  This is a direct rewrite to Jedison's own real keyword, not a mimirheim
  invention — confirmed exactly 5 fields carry `ui_source` today (2 in
  `pv_fetcher`/`pv_ml_learner`'s `output_topic`, 3 in the three baseload
  packages' `mimir_static_load_name`).
- `ui_placeholder` combined with `ui_source` (the `{array_key}` shape, 2
  fields above) → `json_schema_extra={"x-format": "mimir-topic-placeholder"}`
  in addition to the `x-enumSource` key above. The actual custom-editor JS
  behaviour is plan 69's job; this plan only emits the marker.
- `ui_placeholder` with no `ui_source` (a fixed cross-field derivation, no
  per-entry key, e.g. `{mqtt.topic_prefix}/input/prices`) → drop the field
  string entirely and leave the value semantics as they are (`null` = auto-
  derive, unchanged); no schema-level marker is added, since a plain
  `x-watch`/`x-template` pair belongs on the object schema at generation
  time only where it is genuinely needed, and no field today needs it
  without also needing the `{array_key}` custom editor. If this proves
  wrong for a specific field found during the migration, add
  `x-watch`/`x-template` per SPEC §6 and note it in this plan's TDD log
  before proceeding.
- `ui_instance_name_description` → drop entirely, no replacement (SPEC §4).

Every enclosing object schema that now contains at least one field with
`x-category: "Advanced"` must itself carry
`json_schema_extra={"x-format": "categories-vertical", "x-categoryOrder": ["Basic", "Advanced"]}`
at the model's own `ConfigDict(json_schema_extra=...)` level (SPEC §4).

`tests/unit/test_schema_ui_annotations.py` is deleted — it exists solely to
enforce the vocabulary being removed. `scripts/extract_config_docs.py` is
unaffected (confirmed it never reads any `ui_*` key).

## Scope

  `_baseload_variants` deleted.

  redaction round-trip, exclusive-group deletion, placeholder rejection,
  path-traversal 400, IP allowlist, reports mode).
- `mimirheim_helpers/config_editor/README.md` — HTTP API table (§4) updated
  to describe the endpoints as they now actually behave; §2 "How it works"
  step 3 updated to describe file-based discovery instead of importing
  helper config models; §3 "Configuration" gets a note that `config_dir`
  now also has a `schemas/` subdirectory for drop-in schema files (SPEC §2)
  — the discovery mechanism, not just its use.
- `mimirheim_helpers/config_editor/AGENTS.md` — project structure updated
  (`registry.py`, `schemas/bundled/`, `schemas/_meta/`); the "Source of
  truth" note that `SPEC.md` describes a not-yet-implemented target is
  removed for the parts this plan lands (§2, §3, §5, §7, §8, §9, §10 of
  `SPEC.md` become current, not target, once this plan ships — leave the
  note in place for whatever plan 69/70 still haven't implemented).

- The CSP header — tied to the frontend rewrite, plan 69.
- `x-format: "mimir-topic-placeholder"`'s actual rendering behaviour — the
  JS custom editor itself is plan 69's job; this plan only emits the marker
  key in the generated schema.
- Deleting the deprecated aliases — plan 69, once nothing calls them.
- The drop-in authoring CLI, preview endpoint sharing, and wiki page —
  plan 70.

### Files deleted

- `tests/unit/test_schema_ui_annotations.py`.
- `_load_helper_models()` and `_baseload_variants` from `server.py`.

### Step 1 — registry: bundled-only discovery, one test per rejection rule

Write `tests/unit/test_registry.py` against a set of fixture schema files
(not the real bundled ones yet) covering every rule in SPEC §10: oversized
file, invalid JSON, meta-schema failure, non-object root, missing/malformed
`x-mimirheim`, bad `file` pattern, `file` with a path separator, `file`
equal to `config-editor.yaml`, unknown `category`, id collision (bundled vs.
bundled — expect a startup-time hard error per SPEC §2, not a soft
rejection), non-local `$ref`, excessive nesting depth, excessive property
count. One fixture and one test per rule.

Run — all fail (`registry.py` does not exist yet).

### Step 2 — implement discovery and meta-schema validation

Write the meta-schema. Implement `registry.py`'s `discover_bundled()` (or
equivalent) satisfying Step 1. Green.

### Step 3 — drop-in discovery and collision handling

Add tests: a drop-in with a fresh id loads; a drop-in id colliding with a
bundled id is rejected (bundled wins); two drop-ins with the same id,
processed in sorted filename order, first wins and the second is rejected
with a reason naming the winning file; a malformed drop-in never prevents a
valid sibling from loading.

Implement `discover_dropins()` / merge logic. Green.

### Step 4 — context composition

Add tests building `context` (SPEC §5) from a real, in-memory
`mimirheim.yaml`-shaped dict: `mqtt_topic_prefix`, `pv_arrays`,
`static_loads` all present and correctly shaped for a non-`mimirheim.yaml`
entry; `mimirheim.yaml`'s own entry gets no `context` key at all; an empty
`pv_arrays`/`static_loads` produces an empty object, not an absent key.

Implement composition. Green.

### Step 5 — validation model

Add tests: `jsonschema`-only validation for a drop-in even when it declares
`python_model` (ignored, with a logged warning — assert the warning is
logged, assert no import is attempted); two-pass validation for a bundled
entry with `python_model` set, including a case where `jsonschema` passes
but the Pydantic cross-field validator fails (confirms the second pass adds
real coverage, not just duplicate checking); confirm error shape from both
passes is identical.

Implement. Green.

### Step 6 — save semantics

Add tests: validate-all-then-write-all across a dirty set of two entries
where one is invalid — assert neither file is written; both valid — assert
both written atomically; saving a `baseload-ha.yaml` enable deletes
`baseload-static.yaml`/`baseload-ha-db.yaml` if present, driven by
`exclusive_group`, not a hardcoded list; comment preservation on an existing
file survives a save that only touches one field (reuse the existing
ruamel.yaml round-trip mechanism, do not reimplement it).

Implement. Green.

### Step 7 — extend `generate_schema_json.py`

Extend the script to emit one bundled `.schema.json` per Decision 2's table,
each with its `x-mimirheim` envelope. Extend (or add a sibling to) the

Run the script, commit the generated output, run the drift test — green.

## Acceptance criteria

- [ ] `grep` for any helper package name in `config_editor/*.py` returns
      nothing outside `registry.py`'s own `x-mimirheim.python_package`
      string literals used for the installed-check, and outside comments.
- [ ] A malformed schema file (any SPEC §10 rule) never crashes startup and
      never prevents another schema from loading.
- [ ] Every rejection reason names the offending key/file, is actionable,
      and contains no absolute filesystem path.
- [ ] A drop-in declaring `python_model` loads with structural validation
      only, and a warning is logged.
- [ ] Any schema with a non-local `$ref` is rejected.
- [ ] `context` (SPEC §5) is present and correctly shaped for every
      non-`mimirheim.yaml` entry, absent for `mimirheim.yaml`'s own entry.
- [ ] Save is validate-all-then-write-all over the dirty set; a failing
      entry blocks the whole save; untouched files are never rewritten.
- [ ] Exclusive-group deletion is driven by `x-mimirheim.exclusive_group`,
      not a hardcoded list.
- [ ] Comment-preserving atomic YAML writes, MQTT sentinel redaction, the IP
      allowlist, the body size cap, and `_safe_join`'s containment check all
      still function, covered by tests against the new endpoints.
- [ ] No `ui_label`/`ui_group`/`ui_placeholder`/`ui_source`/
      `ui_instance_name_description` string remains anywhere in the
      codebase; `tests/unit/test_schema_ui_annotations.py` is deleted.
- [ ] The six deprecated aliases still work, backed by `registry.py`.
- [ ] `static/app.js` still works unmodified against the deprecated
      aliases (manual smoke check: start the server, load the existing
      frontend, confirm it still renders and saves).
- [ ] `README.md`'s HTTP API table, "How it works" step 3, and
      "Configuration" section accurately describe the shipped behaviour —
      no reference to importing helper config models or to a fixed helper
      list remains.
- [ ] `uv run pytest mimirheim_helpers/config_editor/tests` and
      `uv run pytest` both green.
- [ ] All work is on `feat/config-editor-registry`, not merged or pushed
      without explicit approval.
